# 写代码前先调研目标 App

操作第三方 App 时：**先根据用户原话拆清「有几种对象、有几层列表」，再在真机上把每一种都打开：带图看屏 + 拉节点。** 禁止只 snapshot 当前碰巧停着的那一页，就当界面已经懂了。禁止不看屏只靠节点树猜布局。

相关：[`progress-model.md`](./progress-model.md)、[`segment-test.md`](./segment-test.md)、[`page-state.md`](./page-state.md)、[`device.md`](../../00-core/device.md)。

## 硬规则（MUST）

1. **清单从用户原话拆，不要自行合并。** 并列、顿号、「或 / 和 / 以及」拆成多种对象；没点名的子层默认不是操作目标。
2. **清单上的每一种都要实际打开**，`snapshot --image` 看布局（一屏几条、有没有子层、操作落在哪一区），再拉节点记下 `text` / `desc` / `bounds`。没打开过的 = 尚未支持。
3. **同一文案可以是不同控件。** 按所在区域、所在布局区分，不要全文搜索到谁就点谁。
4. 调研结论写进回复后再落盘选择器。禁止用训练记忆里某 App 的 id / desc 代替当次节点。
5. 写循环前先回答进度模型。见 [`progress-model.md`](./progress-model.md)。

## 怎么从原话拆清单（自己推，不要等文档点名）

| 原话里出现 | 你要当成 | 默认处理 |
|------------|----------|----------|
| 并列的多种对象 | **多种形态**：布局、入口、操作条都可能不同 | 每种都打开、都拉节点、都验收 |
| 列表项里还能再展开 / 更缩进 / 挂在另一条下面 | **子层** | 需求没说要做子层 → 排除，不要当父项 |
| 同一动作出现在详情、列表、半屏、底栏等不同区域 | **多个控件** | 按区域 + 完整特征点，禁止点到相邻控件 |
| 搜索 / 关注 / 收藏等带结果列表 | **结果也是一种形态** | 结果里每种合格样式至少看一条，不要只走最好找的那种 |

互斥特征用当次 `bounds` / 区域 / 完整 `desc`，不要抄其它工程的坐标阈值。

## 调研最小步骤（编写前）

```
1. 从用户原话列出：形态清单、层级清单（父项 / 子层）
2. launch 目标 App，关掉业务弹窗
3. 清单每一项都走到真实界面 → **带图 snapshot** 看布局 + 片段 run 打印关键节点
4. 形态之间、父项与子层之间，对比差异并写下判断规则
5. 数当前屏可见目标数，写清滚动时机（progress-model）之后，才写选择器和主循环
```

某一种暂时走不到：换入口再试，**不能省略**。回复里写已尝试的路径；连续失败再请用户指一条样本。

## 自检

- [ ] 原话里的并列对象都打开过，各有带图 snapshot + 节点 logs
- [ ] 看见可展开 / 缩进的子层时，已决定做或不做，并且选择器能分开
- [ ] 同名动作已按区域区分，不是「搜到文案就点」
- [ ] 没摸到的形态没有写成已支持
- [ ] 进度模型自问表已回答
